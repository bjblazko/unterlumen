# Rotate a photo

*Last modified: 2026-11-15*

## Summary

Turn a photo by 90° left or right, or by 180°, in the viewer, the way Crop
changes it today: in place, in the file. A photo the camera saved sideways,
or one taken straight down, can then be set right without leaving
Unterlumen.

Unterlumen has never had this. It has only ever *read* a photo's
orientation (EXIF tag, HEIF `irot` box, see ADR-0020). The UX review
(`doc/ideas/2026-10-21-ux-review.md`, item 12) and the plan in
[one system for every place](../done/2026-10-21-one-system-for-every-place.md)
(item 12: "rotate go into ⋯; their keys stay") count it as a viewer control
anyway. That was planned and never built.

## Details

### Where it lives

- The viewer's ⋯ menu: *Rotate left*, *Rotate right* (and maybe *Turn
  upside down*). Not in the toolbar: rotating is rare, Crop and Mark for
  deletion stay the visible actions.
- Keys: to be chosen. `R` / `Shift+R` are the obvious ones, but check
  `app-keyboard.js` and the viewer's own handler for collisions first. The
  viewer's handler must ask `App.keyboard._isInputFocused(e)`.
- Several selected photos at once (Folders, a library): later, if at all.
  For more than five files that would run in `ProgressDialog`.

### How the file changes. Decide first, probably in an ADR

Two ways, with different costs:

1. **Rewrite the orientation only.** For a JPEG, set the EXIF orientation
   tag (exiftool `-n -Orientation=…`). The pixels stay as they are, so
   nothing is lost and it is fast. Every reader has to honour the tag, and
   Unterlumen does that already for thumbnails and the viewer. HEIF: the
   `irot` box or the EXIF item, and which one depends on the camera
   (ADR-0020). Writing it safely is the open question.
2. **Turn the pixels and re-encode**, like Crop (`media/crop.go`): decode,
   apply the present orientation, turn, encode, orientation tag to 1. It
   works the same for JPEG, PNG, WebP and HEIF (via sips, macOS only), but
   costs one generation of lossy compression each time.

Option 1 for JPEG and option 2 for the rest is likely. A lossless JPEG
rotation (jpegtran-style) would be a new helper program; see
`huepattl-legal-check` and `credits.json` before adding one.

### What has to follow the change

The same things a crop has to touch, so share that code rather than copy it:

- `media.EvictFile(absPath)` and `ScanCache.Invalidate(dir)`, as in
  `internal/api/crop/handler.go`.
- Browser caches: since 2026-11-15 the photo and thumbnail endpoints answer
  with `no-cache`, so the same address shows the turned photo. The viewer
  still needs its `_cacheBust` for the photo on screen.
- Library index (ADR-0052): the file's SHA-256 changes, so it is a new
  photo ID. `Indexer.retire` replaces the row and records it in
  `photo_replaced`. Faces' boxes and marked regions in the sidecar
  (`xmp_regions.go`) are in image coordinates and must be turned with the
  photo, or every face box ends up beside its face.
- Width and height swap for 90° turns (`p.width`/`p.height` columns,
  aspect-ratio statistics).

## Acceptance criteria

- [ ] Decision on the way of changing the file, per format, recorded as an
      ADR (or as an amendment to ADR-0020).
- [ ] Rotate left / right in the viewer's ⋯ menu, with keys, for JPEG, PNG,
      WebP and HEIF (HEIF on macOS; elsewhere the item says why it is not
      available).
- [ ] After a turn, the viewer, the film strip, the thumbnails in Folders
      and in a library show the turned photo, also after the viewer is
      opened again.
- [ ] Portrait Fujifilm HEIF and an Apple HEIC each turn correctly in all
      four directions, with no double rotation (CLAUDE.md gotchas on HEIF
      orientation).
- [ ] Face regions in the sidecar turn with the photo.
- [ ] Go tests for the turn per format; an e2e spec in `e2e/specs/` for the
      viewer action.
- [ ] README, CHANGELOG and the help on keys updated.
